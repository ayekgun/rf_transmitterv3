## 1. Ringkasan perubahan

Pengecekan Get Delivery Status dimigrasikan dari endpoint Legacy ke Telkomsel API **V2**
(IFA v.5.0 Section E.iv & E.vi) sesuai issue #2.

| Aspek | v1.2.0 (Lama) | v2.0.0 (Baru) |
|---|---|---|
| Method + path | `GET /bank/transaction-status` | `POST /bank/v2/transaction-status` |
| Parameter `transaction_id` | query string | body JSON `{"transaction_id":"..."}` |
| Autentikasi | query param `pwd` | header `X-Signature` = HMAC-SHA256 |
| Header dikirim | — | `Content-Type`, `appsid`, `sid`, `X-Timestamp`, `X-Signature` |
| Sumber kredensial | doc Mongo (`appsid`/`sid`/`pwd`) | doc Mongo (`appsid`/`sid`) + `client_secret` dari **apps_config** |
| HTTP 400 / 405 | masuk retry | **GIVE_UP permanen** (`PERMANENT_ERROR`) |

**Canonical string yang ditandatangani** (6 baris, tanpa trailing newline):

```
POST\n<path>\n<appsid>\n<sid>\n<timestamp>\n<rawRequestBody>
```

`X-Timestamp` = epoch detik. `X-Signature` = HMAC-SHA256(client_secret, canonical) dalam
**hex lowercase** (64 karakter). `<path>` = `encodedPath()` dari `provider_status_url`
(mis. `/bank/v2/transaction-status`).

**Penyimpanan `client_secret`** — prinsip keamanan IFA Section E.iv: secret **tidak** disimpan
di dokumen `dr_pull_telkomsel`. Di-resolve per transaksi dari `apps_config` berdasarkan
`(appsid, sid)` yang tercatat di doc, dengan urutan prioritas:

1. `client_secrets_json` key `"<appsid>:<sid>"`
2. `client_secrets_json` key `"<appsid>"`
3. `client_secret` (fallback tunggal)

Yang **tidak** berubah: status set (`PENDING/PULLING/PUBLISHING/RESOLVED/GIVE_UP`), fencing
`lease_id` (`claimPulling`/`claimPublishing`/`finalizeResolved`/`backoffOrGiveUp`/`giveUp`),
schema Mongo (field `pwd` pada doc lama **diabaikan**, tidak dibaca dan tidak dihapus), serta
format DR message dan SQL INSERT ke hilir (`jns.dr.drrealhandler` & `jns.db.deliveryreport`).

## 3. Prasyarat SIT

1. Artifact `drpulltelkomsel-2.0.0.jar` ter-deploy di `bin/` server target. `start.sh` tidak
   berubah dan memilih jar terbaru lewat `ls drpulltelkomsel-*.jar | sort -V | tail -1` —
   pastikan **hanya satu** jar `drpulltelkomsel-*` yang tersisa (versi lama di-backup ke
   direktori lain).

2. **`client_secret` dari tim Telkomsel sudah diperoleh** (blocker utama). Kumpulkan per
   environment untuk tiap pasangan `(appsid, sid)` yang dipakai transaksi DR Pull. Simpan di
   password manager / `apps_config` saja; **jangan** di repo, form, chat, atau tiket.

3. Config `apps_config.jns_config` (`lookup_type='drpulltelkomsel'`) sudah di-reseed dari
   `doc/sample-apps-config.sql` versi v2.0.0:

   ```sql
   -- cek keberadaan key tanpa mencetak nilainya
   SELECT lookup_name FROM jns_config
   WHERE lookup_type = 'drpulltelkomsel'
     AND lookup_name IN ('provider_status_url', 'client_secret', 'client_secrets_json');
   ```

   - `provider_status_url` **wajib** berupa URL lengkap yang menyertakan path V2
     (`https://<host>/bank/v2/transaction-status`) — dipakai apa adanya, kode tidak
     menambahkan path.
   - Isi `CHANGE_ME` dengan nilai real environment. Skrip bersifat DELETE-lalu-INSERT:
     **jalankan di environment yang benar saja**, karena akan menghapus seluruh baris
     `lookup_type='drpulltelkomsel'` lebih dulu.

4. Pasangan `(appsid, sid)` pada doc uji harus punya entri secret di `client_secrets_json`
   (atau fallback `client_secret`). Untuk doc uji yang memakai mock, cukup:
   `client_secret = <secret sama dengan --secret mock>`.

5. Akses: Mongo `dr_pull_telkomsel`, ActiveMQ (`jns.dr.drrealhandler`,
   `jns.db.deliveryreport`), MySQL `apps_config`, dan `bin/out-drpulltelkomsel.log`.

6. Untuk skenario offline tanpa endpoint Telkomsel asli, jalankan mock V2:

   ```bash
   python3 doc/mock-telkomsel-server.py --port 8089 --secret '<client_secret-uji>'
   # arahkan provider_status_url ke:
   #   http://localhost:8089/bank/v2/transaction-status
   ```

   Mock menegakkan kontrak V2: non-POST → `405/2405`, ada query string → `400/2400`,
   header wajib tidak lengkap / signature salah → `401/2401`.

## 4. Skenario positif

| ID | Skenario | Langkah | Hasil yang diharapkan |
|---|---|---|---|
| P1 | Happy path `D` | Doc `PENDING` due (default prefix trxid), `appsid`/`sid` punya secret | Log `httpStatus=200` → `published provider_status=D`; doc `RESOLVED`; 1 DR + 1 SQL terpublikasi |
| P2 | Happy path `ND` | Sama dengan P1, trxid prefix `MOCK-ND-` | Log `deliveryStatus=ND`; doc `RESOLVED`; DR dengan `provider_status=ND:061` (mock mengembalikan `errorCode=061` seperti contoh resmi §E.vi — kode tidak-000 diserialkan sebagai `ND:<code>`) |
| P3 | Request berbentuk V2 | Tangkap request di mock/proxy pada P1 | Method `POST`, path `/bank/v2/transaction-status`, **tanpa query string**; header `appsid`, `sid`, `X-Timestamp`, `X-Signature` (`[0-9a-f]{64}`) ada semua; `Content-Type: application/json`; body `{"transaction_id":"<trx>"}` |
| P4 | 404 / 2404 → backoff | trxid prefix `MOCK-404-`, `attempt=0` | Log `httpStatus=404`; doc `PENDING`, `attempt=1`, `next_pull_at` ≈ +30 menit, `last_error="2404 transaction not found"`; tidak ada DR |
| P5 | 404 berulang sampai `max_attempt` | `MOCK-404-`, `attempt=4` | Doc `GIVE_UP`, `attempt` tidak naik lagi, `last_error` menyebut max attempt; tidak ada DR |
| P6 | 500 → backoff | trxid prefix `MOCK-500-` | Doc `PENDING`, `attempt+1`; **bukan** `GIVE_UP` |
| P7 | Timeout → backoff | trxid prefix `MOCK-TIMEOUT-` (`timeout_seconds=30`, mock tidur 35s) | Client timeout duluan ±30s, WARN `timeout/IO error`; doc `PENDING`, `attempt+1`; sweep tidak macet, trx lain tetap jalan |
| P8 | Body malformed → backoff | trxid prefix `MOCK-MALFORMED-` | `200` dengan body bukan JSON; `last_error` berawal `body malformed: `; doc `PENDING`, `attempt+1`; tidak ada exception yang menghentikan sweep |
| P9 | Fallback secret per-appsid | Secret hanya di key `"<appsid>"` (bukan `"<appsid>:<sid>"`) | Resolve berhasil, request terkirim, P1 berlaku |
| P10 | Fallback `client_secret` tunggal | `client_secrets_json` kosong/`null`, hanya `client_secret` terisi | Resolve berhasil, P1 berlaku |
| P11 | Kontrak hilir identik | Bandingkan DR message + SQL INSERT hasil P1 dengan v1.2.0 | Field/kolom, format timestamp `yyyyMMddHHmmss`, dan `provider_err` sama persis; engine hilir tidak bisa membedakan sumber push vs pull |
| P12 | Zero double publish | Kirim 1 doc `PENDING`, jalankan 2 instance bersamaan | Hanya **satu** `claimPublishing` menang; DR/SQL terpublikasi tepat sekali; instance kedua log `Skip publish, ... reason=push path already claimed` |
| P13 | Versi & startup | `ps aux \| grep drpulltelkomsel-2.0.0`, `tail out-drpulltelkomsel.log` | Proses jalan versi 2.0.0; log startup bersih tanpa `ERROR`/`Exception`; `provider_status_url` menunjuk path `/bank/v2/transaction-status` |

## 5. Skenario negatif

| ID | Skenario | Langkah | Hasil yang diharapkan |
|---|---|---|---|
| N1 | **400 / 2400 → GIVE_UP permanen** | trxid prefix `MOCK-400-` | Doc **langsung** `GIVE_UP`, `last_error` memuat `2400`; **tidak** ada backoff, `attempt` tidak naik; tidak ada DR. Ini perubahan perilaku vs v1.2.0 |
| N2 | **405 / 2405 → GIVE_UP permanen** | trxid prefix `MOCK-405-` | Doc langsung `GIVE_UP`, `last_error` memuat `2405`; tidak ada backoff, tidak ada DR |
| N3 | 401 / 2401 → GIVE_UP | trxid prefix `MOCK-401-` | Doc langsung `GIVE_UP`, `last_error="credential wrong, give up (telkomsel 401)"`; tidak ada retry, tidak ada DR |
| N4 | Doc tanpa `appsid`/`sid` | Doc `PENDING` due **tanpa** field `appsid` dan `sid` | Doc `GIVE_UP`, `last_error="credential not found in doc"`; **tidak ada HTTP request** ke provider (verifikasi di log mock: jumlah request tidak bertambah) |
| N5 | `appsid`/`sid` ada, secret tidak ketemu | Doc dengan pasangan yang tidak punya entri di config, dan `client_secret` kosong | Doc `GIVE_UP`, `last_error="client_secret not found"`; **tidak ada HTTP request** |
| N6 | `client_secret` salah | Ubah secret jadi nilai salah, restart | Provider balas `401/2401` → doc `GIVE_UP` (`credential wrong`). Jangan rollback dulu — perbaiki secret |
| N7 | **Secret/sid tidak pernah bocor ke log** | `grep -i` nilai secret, nilai `sid`, dan header `X-Signature` di `out-drpulltelkomsel.log` setelah semua skenario | **0 baris** cocok. Log hanya memuat `trx`, `appsid`, dan `endpoint` (scheme+host+port+path) |
| N8 | Secret tidak pernah tersimpan di Mongo | Query doc `dr_pull_telkomsel` setelah P1 | Tidak ada field `pwd`/`client_secret` yang ditulis oleh aplikasi |
| N9 | Doc lama yang masih punya `pwd` | Jalankan app terhadap doc lama berisi `pwd` | Doc terbaca normal tanpa exception; `pwd` **diabaikan** (tidak dibaca, tidak dihapus); alur tetap memakai secret dari config |
| N10 | Method non-POST (validasi mock) | `curl -i http://localhost:8089/bank/v2/transaction-status` (GET) | Mock menjawab `405` + `errorCode=2405` — memastikan mock menegakkan kontrak V2 yang sama dengan provider |
| N11 | Parameter di query string (validasi mock) | `curl -i -X POST 'http://localhost:8089/bank/v2/transaction-status?transaction_id=X'` | Mock menjawab `400` + `errorCode=2400`. Kalau provider asli mengembalikan ini saat SIT, artinya ada parameter yang salah kirim — bukan masalah secret |
| N12 | `provider_status_url` tidak valid | Set URL rusak (mis. tanpa skema), restart, picu sweep | Log `provider_status_url tidak valid`; doc `PENDING` + backoff, tidak ada crash sweep |
| N13 | Config tanpa key secret sama sekali | Hapus `client_secret` dan `client_secrets_json`, restart, picu sweep | Semua doc `PENDING` → `GIVE_UP` alasan `client_secret not found`; aplikasi tetap start tanpa error |

## 7. Urutan deploy (kritis)

1. Peroleh `client_secret` dari tim Telkomsel per `(appsid, sid)` — **blocker**, jangan deploy
   tanpa ini.
2. Backup artefak & config berjalan:
   `cp drpulltelkomsel-1.2.0.jar drpulltelkomsel-1.2.0.jar.bak` dan
   `mysqldump apps_config jns_config --where="lookup_type='drpulltelkomsel'" > backup-$(date +%Y%m%d%H%M%S).sql`
   (tabel `jns_config` **tidak** punya unique constraint sungguhan — backup ini satu-satunya
   referensi rollback config).
3. Uji reachability endpoint V2 dari server target dengan `curl` POST + signature valid
   **sebelum** cutover. Harapan `200`/`404`. Bila `401` → secret atau canonical string salah;
   bila `400` → ada parameter di query string. Jangan lanjut sebelum signature diterima.
4. Reseed config (`provider_status_url` → path V2, tambah `client_secret` +
   `client_secrets_json`).
5. Deploy `drpulltelkomsel-2.0.0.jar`, pastikan hanya satu jar tersisa di `bin/`.
6. `./start.sh stop && ./start.sh start && ./start.sh status`.
7. Pantau 15 menit: tidak ada akumulasi doc `PULLING`, tidak ada lonjakan `GIVE_UP`, tidak ada
   `401/2401` berulang.

## 8. Hasil verifikasi terhadap IFA v.5.0 (resmi)

Semua pertanyaan terbuka sebelumnya sudah dijawab oleh dokumen **IFA SMS Bulk Premium v5.0**
§E.iv (Request Signing), §E.vi (Get Delivery Status V2), §E.ii (DLR), dan §F (Migration).

| # | Pertanyaan | Jawaban spec | Status implementasi |
|---|---|---|---|
| 1 | Newline di akhir canonical string? | **Tidak ada** — "six values joined with a single newline, with no trailing newline" | ✅ Sesuai |
| 2 | `X-Timestamp` detik atau milidetik? | **Epoch detik**, wajib dalam **±300 detik** dari jam server Telkomsel | ✅ Sesuai (epoch detik) |
| 3 | Urutan canonical string? | `METHOD\nPATH\nappsid\nsid\ntimestamp\nrawRequestBody` | ✅ Sesuai persis |
| 4 | Body error: HTTP status atau bisa 200? | Tabel spec memetakan **1:1**: `400→2400`, `401→2401`, `404→2404`, `405→2405`, `200→sukses`. Tidak ada kombinasi 200+error | ✅ Pemetaan berbasis status code **benar** |
| 5 | Bentuk body error | `{"error":true,"error_code":2400,"message":"..."}` — `error_code` **Integer snake_case**; body sukses memakai `errorCode` **String** | ⚠️ Kode tidak membaca body error (memetakan dari status) — aman, tapi jangan tertukar saat menulis test |
| 6 | Rollback masih berguna? | Legacy masih aktif saat cutover (konfirmasi @rayzalzero) | ✅ Rollback di CRD valid |

**Vektor turunan formula kini terkunci di `HmacSignerUtilTest`** (2 test). Spec §E.iv **tidak
memuat vektor numerik** — yang ada hanya contoh bash dengan placeholder. Nilai di bawah
dihitung lokal dengan pipeline `openssl` yang sama dengan contoh spec, memakai secret karangan
(`test-secret-123` / `spec-example-secret`), jadi fungsinya mengunci implementasi terhadap
formula §E.iv, bukan mencocokkan angka dengan spec:

| Input | Nilai `X-Signature` |
|---|---|
| `/bank/v2/transaction-status`, `cp_sample`/`sender_sample`, ts `1763436000`, secret `test-secret-123` | `af938430b9d793c39a15aa177e3445b04e59f1db8bee7b71a0dca0a86e08ff19` |
| `/bank/v2/pushbulk` + body OTP dari contoh §E.iv, secret `spec-example-secret` | `78ff95c89f0bee6bade042b32aaf4ce0ffbee04be4365f1675c848a8979e32ae` |

### Risiko operasional baru: jam server wajib NTP (±300 detik)

Spec §E.iv: timestamp di luar **300 detik** dari jam server Telkomsel ditolak sebagai
**authentication error (401/2401)**. Karena v2.0.0 memetakan `401/2401` ke **GIVE_UP permanen**,
server dengan jam drift > 5 menit akan membuat **seluruh** transaksi `PENDING` langsung
`GIVE_UP` tanpa retry — dan pemulihannya butuh reset manual di Mongo.

Wajib sebelum cutover: `timedatectl` / `chronyc tracking` menunjukkan sinkronisasi NTP aktif di
server aplikasi. Bila jam pernah drift, periksa doc yang terlanjur `GIVE_UP` dengan
`last_error="credential wrong, give up (telkomsel 401)"` — **bukan** tanda secret salah.

### Catatan lain dari spec

- **Format `trx_id` V2 berubah** (dari "alphanumeric max 20" menjadi **6–64 karakter**, hanya
  `[A-Za-z0-9._-]`). Dicek terhadap `doc/smsCore.dr_pull_telkomsel.json`: **11/11 doc produksi
  sesuai** — tidak ada risiko data lama.
- **Rotasi secret = hard cutover.** Telkomsel hanya menyimpan **satu** secret per partner;
  request bertanda tangan secret lama langsung gagal begitu secret baru aktif. Waktu switch
  harus disepakati dengan Telkomsel, dan `client_secret`/`client_secrets_json` di `apps_config`
  diperbarui + restart **pada saat yang sama**.
- **Semua kegagalan autentikasi memakai pesan generik yang sama** (missing header, timestamp
  kedaluwarsa, partner tidak dikenal, signature salah) — log provider tidak akan menunjukkan
  bagian mana yang salah. Diagnosis harus dari sisi kita.

### Gap yang masih tersisa

1. **`doc/archive/UAT-test-plan-v1.2.0.md` adalah dokumen arsip** — sengaja dipertahankan
   sebagai referensi rilis 1.2.0 dan **tidak boleh** dipakai untuk testing v2.0.0 (masih menyebut
   `pwd`, `lease_minutes`, `auth_error_backoff_minutes`, `LeaseResetTask`, `PUSH_RESOLVING`, dan
   email alert — semuanya sudah tidak ada). Acuan testing v2.0.0 adalah dokumen ini.
2. **Uji terhadap endpoint Telkomsel asli belum dilakukan** — vektor turunan formula sudah
   terbukti cocok secara matematis (§8), tetapi penerimaan oleh provider (bukan 401) tetap gate
   wajib sebelum UAT. Bila masih 401 padahal secret benar, periksa **jam server** (NTP) dulu
   sebelum menyalahkan secret.
